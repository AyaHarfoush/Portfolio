Graduation Project

QR and URL Phishing Detection: A Machine Learning Based Approach

A Flask web application that detects phishing in both URLs and QR codes inside one unified system. The user either scans a QR code or enters a link directly, and the app classifies it as Safe, Suspicious or Malicious, then explains the specific reasons behind its decision.

The Idea

The project solves the phishing problem found in links and QR codes by using machine learning together with a layer of programmed rules. The goal is to analyze a link, extract features from it, and classify it with high accuracy. The results were accurate and the system detects more than one type of attack, such as brand impersonation, XSS and a specific type of SQL injection.

Architecture

It is a Flask-based web application that follows a client-server architecture. Flask receives the link from the form, converts it into numeric data, and the backend processes it using the machine learning model.

Why Random Forest

A model without an algorithm is just an empty file. The Random Forest algorithm is what gives the model its intelligence. I chose it because it handles complex non-linear data well and reduces the problem of overfitting, which gives high accuracy when detecting diverse phishing links.

Dataset

I used the UCI Phishing Websites dataset, which is prepared data based on the research paper "Phishing Website Features Extraction Based on Heuristic Evaluation" published by Prof. Rami Mohammad. The dataset contains the features already extracted from each website, and my design decisions (such as the dots threshold below) are based on that paper and on statistical analysis of the data.

How I Trained the Model

  • Collected the data and extracted the features.
  • Chose the suitable algorithm (Random Forest).
  • Studied the relationships between the 31 features to understand the patterns that separate phishing sites from legitimate ones.
  • Split the data into a training set and a testing set.

Libraries

  • Flask: connects the front end with the back end.
  • pandas: reads the whole dataset.
  • scikit-learn: lets the computer learn the rules from the data.
  • joblib: moves the trained model from the training stage to the running application.
  • tldextract: extracts the domain parts of a URL.

Two Layers of Detection

Heuristic Engine (rules written in code)
  • SQL Injection
  • XSS
  • Brand Impersonation
  • IP-Based URL
  • Open redirect attacks
  • Random-looking domain patterns
Random Forest Model (detected by the model)
  • URL length attack
  • Double slash redirection
  • URL shortening services
  • Missing HTTPS encryption

The rules are only primary filters that help the user understand why a link is suspicious. The final decision, and the high-confidence percentage, comes from the model based on the features.

Explainable Results

The app does not only say "malicious" or "safe". It gives the specific reasons behind each classification, telling the user why the link is malicious or why it is safe.

Design Decisions

  • Missing HTTPS: the https check is one of the extracted features. If a link does not start with https, the dataset treats that site as lacking encryption, so it is counted as a reason to be suspicious. A browser will only start a link with https if the server was checked and has a valid SSL certificate.
  • More than 3 dots: a rule warns that the link is suspicious if it has more than 3 dots. The number comes from statistical analysis of the UCI dataset (the having_sub_domain column). Normal links can contain up to 3 dots, so lowering the threshold would flag real, trusted links as suspicious (false positives).
  • Spaces in links: tldextract does not support spaces inside real web links, so a link containing spaces cannot give a correct result.
  • A link ending with ?id=1: this is treated as a normal query, found on millions of trusted sites, because the site is just asking the database to show product number 1. An injected link instead contains symbols that force the database to break the original query and run a different command.

Testing with Real Links

URLhaus links mostly focus on malware distribution, so they use clear and direct words such as bin, exe, dll or random domain names. PhishTank links focus on stealing information: they look technically clean, use https and subdomains that look official, and contain no suspicious words. The system handles both styles through the combination of the rules and the model.

Scope and Limitations

The project focuses on phishing links. Traditional SQL injection happens after the user enters the website and depends on what is typed into inputs such as username or password, not on the shape of the link. However, some attacks of this type place the SQL commands inside the link itself, and that is what my program can detect. It does this through static analysis: it checks the URL text and searches for SQL signatures such as union select, drop table and insert into. It does not protect a database.

CSRF is not covered because it cannot be detected from the link alone. CSRF links look clean and valid, and the attack happens through scripts injected into the link while the user is already logged in to a site.
